Jenna: Epic Integration Documentation

How Jenna, Top Health AI's AI receptionist, connects to Epic via FHIR STU3 and SMART on FHIR Backend Services to check availability and book appointments on behalf of callers.

1.Overview

Jenna is a voice AI receptionist for ambulatory practices. Patients call the practice's normal phone line and speak with Jenna, who checks real-time appointment availability and books appointments directly against the practice's live schedule.

Top Health AI LLC provides Jenna as a subscription SaaS product, billed per provider or per location. Revenue is not tied to API call volume. The integration is used only to fulfill scheduling requests made during real calls.

Jenna's Epic connection is a backend service: there is no interactive user login, no embedded app launch, and no SSO. The application authenticates as itself and calls the FHIR API directly.

2.Authentication

Jenna uses SMART on FHIR Backend Services (OAuth 2.0 client credentials with a signed JWT assertion). No client secret is transmitted over the wire.

  1. An RSA key pair is generated for the application; the public key (JWK) is registered with Epic at app registration.
  2. At runtime, Jenna's backend signs a JWT assertion with the private key.
  3. The signed assertion is exchanged for a short-lived bearer access token at the organization's token endpoint.
  4. Tokens are cached until expiry and refreshed automatically, so no token is requested per caller interaction.
POST /oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion={signed_jwt}

The private key never leaves the backend service environment. It is encrypted at rest and is not accessible to the calling application, the voice platform, or any client-side system.

3.FHIR resources & scopes

Jenna's confirmed usage centers on the Appointment resource in FHIR STU3, accessed through Epic's $find and $book operations. No clinical, financial, or documentation scopes are requested.

ResourceOperationUsed for
Appointment (STU3)$findSearching for real, currently-open appointment times for a given provider, department, and visit type
Appointment (STU3)$bookBooking a returned slot once the caller selects a time

Any additional resource access required to support these two operations is scoped as narrowly as possible and finalized against each connected organization's own FHIR conformance statement.

4.Patient identity matching

Patient identity is resolved as part of the $find request itself. Jenna passes the caller's first name, last name, date of birth, and a secondary identifier (phone number) as demographics on the request, and Epic matches and returns the corresponding Patient reference directly in the response.

If the demographics given don't resolve to a single clear match (for example, family members with identical demographic details), Jenna asks a brief confirming question before proceeding rather than guessing.

5.Scheduling workflow

Booking

  1. The caller states their visit reason, provider preference, and date/time preference.
  2. Jenna authenticates, then calls Appointment.$find (STU3) with the caller's demographics, department, visit type, provider, and date range.
  3. The request returns real candidate slots along with the matched patient reference (see Patient identity matching above).
  4. The caller selects one of the returned times. Jenna never offers or books an invented time.
  5. Jenna calls Appointment.$book against the selected slot and reads the confirmation back to the caller.
Same-day safeguard. When a caller requests the current day, Jenna checks the current time before searching, and silently filters out any slot that has already passed, so a caller is never offered, or able to book, a time that's already gone.

6.Error handling

  • Authentication failures (401/403) trigger one automatic token refresh and retry.
  • Rate-limit (429) and server (5xx) responses are logged, not silently retried. There are no infinite retry loops.
  • Booking actions fail safe: nothing is submitted twice, and a failed booking is reported to the caller rather than assumed to have succeeded.
  • Failed transactions are logged with a timestamp and request ID for troubleshooting.

7.Data handling & security

  • All API traffic is encrypted in transit (TLS 1.2+).
  • The signing key, tokens, and configuration are encrypted at rest and restricted to the backend service runtime. It is never exposed to the caller, the voice platform, or any browser context.
  • Operational logs capture timestamps, request IDs, endpoints, and status codes; patient information is minimized or masked in logs.
  • Jenna performs scheduling actions only. No clinical notes, diagnoses, or orders are created or modified.
  • Non-production and production environments are fully isolated from one another.
  • Access is restricted to Top Health AI's engineering team, with role-based access limited to maintenance and troubleshooting; no third-party end users have access to credentials.

8.Operational behavior

  • All calls are event-driven, triggered by an actual caller request. There is no background polling or bulk data extraction.
  • Provider, department, and appointment-type configuration is supplied per practice as static setup information by the practice's own Epic team, not retrieved through a generic lookup API.
  • Appointment searches stay within standard availability search windows and comfortably within published API rate limits.
  • No installation is required on the practice's end. The integration is entirely cloud-based and credentialed per connected organization.
